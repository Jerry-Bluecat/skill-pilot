# 交接卡：检查更新——边查边显示、可逐条更新、提速

> 2026-10-11 由 Claude（主控）派给 Codex。需求正本 `PLAN.md`（先读开头“方向调整”引言，§4.4），上一轮 `docs/fix-usage-lock-report.md`。这是用户真实使用中提出的问题，只做本卡内容。

## 用户原话要点

“点了一下，界面没有任何反应，不知道进度在哪里。最好点完之后，检测到一个更新就先显示一条；同时显示一共有多少个、还差多少没扫描。扫出一个更新之后，就马上在那一条后面接一个更新按钮，我可以直接更新，不用等全部扫描完。”

## 主控实测（只读）

用户 03:59:48 按下“检查更新”，到 04:09:50 仍未结束：已拉取 15 个仓库，卡在最后一个；页面只显示“正在读取上游历史和新版内容，请稍候…”。原因：
- 已撤下（没分配给任何 agent）的 33 个技能也在检查，其中 ResumeSkills 21 个、taste-skill 8 个；
- 每个仓库都 `git fetch` 默认分支历史和对象（`git -C <tmp>/repo-… fetch --depth 1 origin <sha>` 逐个执行），串行；
- 一个仓库慢会拖住全部，没有单仓库超时。

## 要做的

1. **边查边显示**：检查改为后台任务。看板顶部立即显示“共 N 个技能 / M 个仓库，已查 x，剩 y，正在查：<仓库名>”。每查完一个技能，有更新就立刻追加一条（技能名、改了什么、脚本提醒、本机是否改过）；没更新的计入“已是最新”。全部结束后显示汇总。页面刷新或重开后能接上正在进行的任务。
2. **逐条更新**：每条有更新的结果后面直接有“更新”按钮（本机改过的默认用上游的，可改“保留我的”），点了就只更新这一个技能，不必等扫描结束；同时保留“更新全部已查出的”。逐条更新与仍在进行的扫描互不干扰：写前只核对这一个技能的状态，不因整体版本号变化而拒绝；扫描后续发现的结果不覆盖已更新的条目。
3. **提速**：
   - 只检查至少分配给一个 agent 的技能；已撤下的不查（“已撤下”页可单独查）。
   - 先用便宜的方式判断有没有变化：用 `gh api` 取上游该目录当前的 tree sha，与基准比较；相同就直接算“已是最新”，不拉历史。只有不同、或基准不可靠时，才拉历史做细比较。
   - 按仓库并行（并发上限 4），单个仓库设超时（如 60 秒），超时记为“这个没查成，可以稍后重试”，不拖住其他。
   - 同一仓库的多个技能只拉一次。
4. 飞书（lark-cli `--check`）作为一条普通结果参与进度显示。
5. 补单测：后台任务进度与逐条结果、刷新后续接、逐条更新不受扫描影响、已撤下不查、tree sha 相同不拉历史、超时不阻塞。

## 可读 / 可写范围

- **可写**：`~/Developer/skill-pilot/`（不要 commit、push）、系统临时目录。
- **只读**：真实 home 的一切（`~/.skill-pilot/`、四个技能根、Codex 配置、来源记录）。对真实 home 运行本工具一律带 `SKILL_PILOT_READ_ONLY=1`。
- **禁止**：结束或干扰用户正在运行的看板进程；对真实 home 做任何更新、分配、清理；改启动器。
- 网络：只读请求。
- 硬性约束：`skill_pilot/` 代码总行数（`find skill_pilot -name "*.py" -o -name "*.js" -o -name "*.html" | xargs wc -l`，当前 4,321）净增不超过 150 行，能删的旧逻辑删掉。

## 验收方式

- 真实 home 只读跑一次检查（`SKILL_PILOT_READ_ONLY=1`，CLI 或看板均可），记录总耗时和第一条结果出现的时间，写进报告；目标是第一条结果 30 秒内出现、全部完成明显快于 10 分钟。
- 模拟 home 中：看板点检查后立即有进度；结果逐条出现；对第一条点“更新”成功且扫描继续；刷新页面后进度接上；一个仓库人为超时不影响其他。
- 所有单测通过。主控会对比真实 home 指纹（并用操作记录区分用户自己在看板上的操作），任何越界改动都算违规。
